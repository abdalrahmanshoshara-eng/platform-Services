أنت مهندس برمجيات Senior ومتخصص في تصميم لوحات الإدارة الاحترافية، وNext.js، وDjango REST Framework، وUX للأنظمة المؤسسية.

لدي منصة SaaS داخلية مبنية بالفعل باستخدام:

* Django وDjango REST Framework للـBackend.
* Next.js وTypeScript للـFrontend.
* PostgreSQL.
* نظام مستخدمين وخدمات داخلية وخارجية.
* خدمات يمكن تفعيلها وتعطيلها.
* قيود تسمح بحرمان مستخدم من خدمة أو مجموعة خدمات.
* أدوات داخلية تنتج Jobs وملفات.
* خدمات خارجية يتم فتحها من المنصة.
* نظام Analytics وAudit موجود أو تم إنشاء أساسه.

المشكلة الحالية أن حساب الـAdmin ولوحة التحكم غير احترافيين وغير واضحين، ويتم التعامل مع المدير تقريبًا مثل المستخدم العادي.

أريد منك إعادة تصميم وبناء تجربة الإدارة بالكامل بحيث تكون لوحة تحكم إدارية مستقلة، واضحة، منظمة، قوية، وقابلة للتوسع.

لا أريد مجرد تحسين ألوان أو إضافة بعض البطاقات. أريد إعادة بناء Information Architecture وUX الخاصة بالإدارة، مع الحفاظ على المعمارية الحالية وعدم كسر وظائف المنصة.

# 1. الهدف الأساسي

بناء Admin Control Center مستقل عن تجربة المستخدم العادي.

يجب أن يتمكن المدير من:

* إدارة جميع المستخدمين.
* تفعيل وتعطيل الحسابات.
* حظر مستخدم من خدمة واحدة.
* حظر مستخدم من عدة خدمات دفعة واحدة.
* حظر مستخدم من تصنيف كامل من الخدمات.
* إزالة الحظر.
* تحديد سبب الحظر.
* تحديد مدة مؤقتة للحظر عند الحاجة.
* إدارة الخدمات.
* تفعيل وتعطيل أي خدمة.
* تعديل خصائص الخدمة.
* إدارة الإعدادات الخاصة بكل خدمة.
* إدارة مكونات فرعية داخل خدمة، مثل قوالب التقارير.
* مشاهدة إحصائيات عامة عن المنصة.
* مشاهدة إحصائيات مستقلة لكل خدمة.
* متابعة Jobs والعمليات الفاشلة.
* مراجعة سجل الإجراءات الإدارية.
* معرفة حالة المنصة والخدمات من مكان واحد.

يجب ألا يشعر المدير بأنه مستخدم عادي لديه زر إضافي باسم “الإدارة”.

يجب أن يمتلك المدير:

* Layout مستقلًا.
* Navigation مستقلة.
* Dashboard مستقلة.
* صلاحيات مستقلة.
* صفحات مستقلة.
* مكونات UI مناسبة للإدارة.
* تجربة Desktop-first احترافية مع دعم Responsive.

# 2. افحص المشروع أولًا

قبل تنفيذ أي تعديل:

1. افحص بنية الـFrontend والـBackend الحالية.
2. حدد صفحات الإدارة الموجودة حاليًا.
3. حدد Models وEndpoints الحالية الخاصة بـ:

   * المستخدمين.
   * الخدمات.
   * القيود.
   * الإحصائيات.
   * Jobs.
   * Audit Logs.
   * إعدادات الخدمات.
4. حدد ما يمكن إعادة استخدامه.
5. لا تحذف الوظائف الحالية دون فهمها.
6. لا تغير عقود APIs العاملة إلا عند وجود سبب واضح.
7. وثق أي تغييرات معمارية.
8. إذا كانت بعض APIs غير كافية، وسّعها بصورة منظمة بدل وضع حلول مؤقتة في الـFrontend.

بعد الفحص، قدم خطة قصيرة ثم نفذ التعديلات فعليًا.

```text

├── المستخدمون
├── الخدمات
├── التصنيفات
```

* صفحة كاملة للعمليات المعقدة.
* خطوات Wizard عند تعديل إعدادات كثيرة.

# 8. Bulk User Restrictions

أريد دعمًا واضحًا لحالات مثل:

* منع مستخدم من ثلاث خدمات.
* منع مستخدم من جميع أدوات الصور.
* منع عدة مستخدمين من خدمة واحدة.
* إزالة القيود عن مجموعة مستخدمين.

نفذ هذا من خلال APIs منظمة وAtomic Transactions.

لا ترسل عشرات الطلبات المنفصلة من الـFrontend إن كان يمكن تنفيذ العملية في طلب Bulk واحد.

أمثلة APIs مناسبة:

```text
POST /api/v1/admin/user-restrictions/bulk-create/
POST /api/v1/admin/user-restrictions/bulk-remove/
POST /api/v1/admin/category-restrictions/bulk-create/
POST /api/v1/admin/category-restrictions/bulk-remove/
```

يجب التحقق من:

* صلاحية المدير.
* وجود المستخدمين والخدمات.
* عدم إنشاء قيود مكررة.
* تسجيل Audit Event واحد منظم مع التفاصيل.
* إرجاع Summary واضح للنتيجة.

# 11. الإعدادات الخاصة بكل خدمة

لا تفترض أن جميع الخدمات لها الإعدادات نفسها.

أنشئ Service Settings Architecture تسمح لكل خدمة بتوفير إعدادات خاصة بها.

استخدم أسلوبًا قابلًا للتوسع مثل:

* Service Settings Registry.
* Settings Schema.
* Custom Admin Panel Component عند الحاجة.
* Generic Form للخدمات البسيطة.
* Custom Form للخدمات المعقدة.

مثال:

```text
service_key: report_generator
settings_handler: ReportGeneratorSettings
```

لا تضع شروطًا ضخمة في مكون واحد مثل:

```typescript
if service === "reports" ...
else if service === "excel" ...
else if service === "images" ...
```

استخدم Registry أو Mapping منظم.

# 12. إدارة خدمة التقارير والقوالب

لدي خدمة تقارير تسمح بإنشاء ملفات Word أو PDF من قوالب.

يجب أن تمتلك هذه الخدمة لوحة إعدادات خاصة داخل صفحة الخدمة.

أنشئ قسمًا أو صفحة مثل:

```text
/admin/services/report-generator/templates
```

أو ضمن تفاصيل الخدمة إذا كان ذلك أوضح.

## جدول القوالب

اعرض:

* اسم القالب.
* الرمز أو Slug.
* نوع التقرير.
* الإصدار.
* الحالة.
* عدد مرات الاستخدام.
* آخر استخدام.
* تاريخ الإنشاء.
* آخر تعديل.
* الإجراءات.

## حالات القالب

```text
مسودة
مفعل
معطل
مؤرشف
```

## إجراءات القالب

* إضافة قالب.
* تعديل البيانات الوصفية.
* رفع ملف Word جديد.
* إنشاء إصدار جديد.
* تفعيل القالب.
* تعطيل القالب.
* أرشفة القالب.
* معاينة الحقول.
* اختبار إنشاء تقرير.
* مشاهدة الإحصائيات.
* مشاهدة سجل التعديلات.

عند تعطيل قالب:

* لا تحذف القالب.
* لا تسمح بإنشاء تقارير جديدة منه.
* لا تؤثر على التقارير القديمة.
* اسمح برسالة توضح سبب عدم توفره.
* سجل سبب التعطيل.
* سجل المدير الذي عطله.
* سجل التاريخ.
* اسمح بإعادة تفعيله لاحقًا.

## حقول نموذج القالب

اعرض حقول النموذج بصورة مفهومة:

* اسم الحقل.
* Label.
* النوع.
* مطلوب أو اختياري.
* القيمة الافتراضية.
* الترتيب.
* خيارات الاختيار.
* قواعد Validation.

لا تجعل المدير يعدل JSON مباشرة إلا في الوضع المتقدم.

## إحصائيات القالب

لكل قالب:

* عدد مرات الاستخدام.
* المستخدمون الفريدون.
* عدد الملفات المنشأة.
* النجاح والفشل.
* متوسط زمن الإنشاء.
* آخر استخدام.

# 18. صلاحيات الإدارة

لا تعتمد فقط على ظهور رابط `/admin`.

يجب فرض الصلاحيات في الـBackend.

أنشئ Permission Classes واضحة.

حاليًا يوجد ADMIN وUSER، لكن اجعل البنية قابلة مستقبلًا لإضافة صلاحيات أدق مثل:

```text
users.view
users.manage
services.view
services.manage
analytics.view
jobs.manage
audit.view
settings.manage
```

لا تنفذ نظام Roles معقدًا إن لم يكن موجودًا، لكن لا تجعل الكود مغلقًا على شرط واحد منتشر مثل:

```python
if user.role == "ADMIN"
```

يفضل إنشاء Admin Permission Service أو Permission Classes مركزية.

في الـFrontend:

* استخدم Route Guard.
* لا تعرض صفحات الإدارة للمستخدم.
* تعامل مع 401 و403 بصورة صحيحة.
* لا تعتمد على الحماية في الـFrontend فقط.

# 23. الأداء

* `select_related`.
* `prefetch_related`.
* Database indexes.
* Aggregations منظمة.

# 25. حالات خاصة مهمة
